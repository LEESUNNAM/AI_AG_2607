# 리서치 보고서 (docx)

주제 하나만 주어졌을 때, 구조화되고 출처가 명확한 .docx 보고서를 만들어 `research/` 폴더에 저장합니다 — `research/GPU_시장조사_보고서_2026.docx`와 동일한 형태입니다: 표지, 개요, 목차, 번호가 매겨진 섹션, 그리고 링크가 걸린 출처 목록.

## 왜 이런 형태인가

리서치 보고서는 독자가 한눈에 무엇이 담겨 있는지 알 수 있어야 하고(표지 + 목차), 주장을 검증할 수 있어야(진짜 출처 목록, 감이 아니라) 비로소 쓸모가 있습니다. 섹션 구조는 실제 애널리스트가 조사 결과를 정리하는 방식을 그대로 따릅니다: 먼저 맥락, 그다음 실질적인 주제별 내용, 그다음 종합, 그리고 마지막으로 근거 자료. 가볍게 요청받은 경우라도 참고자료 섹션을 생략하지 마세요 — 링크 없는 주장이나 지어낸 내용이 들어간 문서는 보고서가 아닙니다.

## 1. 주제 확정하기

대부분의 요청은 이미 충분히 구체적일 것입니다 ("2026년 GPU 시장 동향", "AI 에이전트 프레임워크 비교"). 주제가 정말로 한 번에 조사하기엔 너무 넓다면 (예: 그냥 "AI"나 "경제"), 추측하지 말고 사용자에게 범위를 좁혀달라고 요청하세요 — 범위가 없는 주제로 만든 보고서는 결국 모든 항목이 얕아집니다. 유추할 수 있거나 기본값으로 정할 수 있는 것들은 굳이 물어보지 마세요:
- **언어**: 사용자가 질문하는 언어에 맞추세요 (이 프로젝트는 기본적으로 한국어).
- **깊이/분량**: 사용자가 더 짧게 또는 심층 분석을 요청하지 않는 한, 중간 정도 깊이의 보고서(대략 GPU 보고서 수준 — 본문 섹션 5~8개, 출처 15~25개)를 기본으로 합니다.
- **독자/문서 구분**: 사용자가 명시하지 않으면 "참고용"/일반 참고자료를 기본값으로 합니다 (예: "교수님께 드릴 보고서"처럼 명시하면 그에 맞춥니다).

## 2. WebSearch/WebFetch로 조사하기

`WebSearch`로 출처를 찾은 다음, 유망한 결과에 `WebFetch`를 사용해 실제 내용을 가져오세요 — 검색 스니펫만 보고 작성하지 마세요. 주요 주장마다 서로 독립된 여러 출처를 폭넓게 확보하는 것을 목표로 하고, 같은 기사 하나를 다섯 번 반복 인용하지 마세요:

- 애그리게이터성 스팸보다 1차 출처와 신뢰할 수 있는 매체를 우선하세요.
- 시간에 민감한 내용(가격, 시장 규모, 제품 로드맵 등)은 게시일을 함께 기록하세요 — 독자는 그 수치가 얼마나 최신인지 알아야 하며, 조사기관마다 수치가 자주 충돌하는데 그런 경우 하나를 임의로 골라 조용히 넘어가지 말고 그 사실 자체를 언급하세요(GPU 보고서의 "조사기관별로... 편차가 존재" 문구 참고).
- 진행하면서 `(출처 제목, url)` 목록을 계속 기록해두세요 — 참고자료 섹션에 그대로 필요하며, 나중에 다시 짜맞추면 링크가 틀리거나 깨지기 쉽습니다.
- 특정 주제에 대해 실제로 다뤄진 자료가 거의 없다면, 억지로 내용을 부풀리지 말고 보고서에 그 사실을 그대로 밝히세요.

## 3. 쓰기 전에 목차부터 구성하기

조사를 마친 *후에* 결과를 섹션으로 묶으세요, 미리 정해두지 말고 — 사전에 정한 템플릿에 데이터를 억지로 끼워 맞추기보다, 실제로 찾아낸 내용이 구조를 결정하게 하세요. 전형적인 형태는 다음과 같습니다:

1. 서론 (맥락: 이 보고서가 무엇을 다루는지와 그 이유)
2. ~ N-2. 주제별 섹션 (주요 테마마다 하나씩; 섹션 안에 명확한 하위 주제가 있다면 GPU 보고서의 "3.1 NVIDIA"처럼 레벨 2 하위 섹션을 사용)
3. 종합 시사점 및 전망 (종합 — 각 섹션 요약을 그냥 반복하지 말고 서로 연결지어 해석)
4. 참고자료 (인용한 모든 출처를 빠짐없이, 인용하지 않은 것은 넣지 않기)

이 최종 목차를 바탕으로 [목차] 섹션을 작성하고, 헤딩 텍스트를 정확히 일치시키세요 — 실제 내용과 어긋난 목차는 아예 없는 것보다 못합니다.

## 4. 문서 만들기

python-docx 호출을 손으로 직접 작성하기보다, 저장소 루트의 `scripts/create_docx.py`에서 `DocBuilder`를 import해서 쓰세요 — 이미 맑은 고딕/한글 폰트 관련 이슈, 기본 크기(제목 40pt/본문 20pt), 이 프로젝트 문서 전반에 쓰이는 메인컬러 테마 처리를 다 해결해 놓았습니다.

```python
import sys
sys.path.insert(0, "scripts")
from create_docx import DocBuilder

doc = DocBuilder(title="그래픽카드(GPU) 시장조사 보고서", main_color="1F4E79")
doc.add_subtitle("2026년 최신 동향 분석")
doc.add_metadata([
    "작성일: 2026년 8월 6일",
    "문서 구분: 참고용",
])
doc.add_divider()

doc.add_heading("[개요]", level=1)
doc.add_paragraph("본 보고서는 ...")

doc.add_heading("[목차]", level=1)
doc.add_paragraph("1. 서론\n2. 시장 규모 및 성장 전망\n3. 주요 기업 동향\n   3.1 NVIDIA\n...")

doc.add_divider()
doc.add_heading("1. 서론", level=1)
doc.add_paragraph("...")

doc.add_heading("3. 주요 기업 동향", level=1)
doc.add_heading("3.1 NVIDIA", level=2)
doc.add_paragraph("...")

doc.add_references([
    ("NVIDIA Q2 FY26 Earnings Release", "https://..."),
    ("Tom's Hardware, \"Desktop GPU roadmap\"", "https://..."),
])

doc.save("research/GPU_시장조사_보고서_2026.docx")
```

여기서 관련 있는 `DocBuilder` 메서드: `add_title` (생성자에서 설정), `add_subtitle`, `add_metadata` (작성일 등 작은 중앙정렬 안내 줄), `add_divider` (섹션 구분선), `add_heading(level=1|2|3)`, `add_paragraph`, `add_bullet_list`/`add_numbered_list`, `add_table`, `add_references` (번호가 매겨진, 실제로 클릭 가능한 하이퍼링크), `add_page_break`. 섹션 번호("1.", "3.1")는 직접 헤딩 텍스트에 적어 넣는 리터럴 텍스트입니다 — 빌더가 자동으로 번호를 매겨주지 않습니다.

사용자가 특정 브랜드/메인컬러를 요청하면 생성자에 `main_color="RRGGBB"`로 전달하고, 그렇지 않으면 스크립트 기본값(`1F4E79`)을 그대로 쓰면 됩니다.

## 5. 저장하고 결과 보고하기

`research/<주제>_조사_보고서.docx` 형태로 저장하세요 (기존 `GPU_시장조사_보고서_2026.docx` 네이밍처럼 파일명에 한글 주제를 사용), 필요하면 `research/` 폴더를 새로 만드세요 — `DocBuilder.save()`가 상위 디렉터리를 알아서 생성합니다.

저장 후 채팅에서 사용자에게 알려주세요: 파일 경로, 보고서가 다루는 내용에 대한 2~3문장 요약, 사용한 출처 개수, 그리고 조사 결과가 빈약했던 부분이 있다면 그것도 짚어주세요. 보고서 전문을 채팅에 그대로 붙여넣지 마세요 — .docx 파일 자체가 결과물입니다.

## 예외 상황

- **주제에 대한 신뢰할 만한 자료가 거의 없는 경우**: 서론과 채팅 요약 둘 다에 그 사실을 명확히 밝히세요. 빈약한 자료를 억지로 늘려 완결된 보고서처럼 꾸미지 마세요.
- **출처마다 수치가 서로 다른 경우**: 범위를 보고하고 두 출처를 모두 인용하세요, 하나를 조용히 골라잡지 마세요 (2절 참고).
- **사용자가 웹 조사 대신 직접 자료를 제공하는 경우**: WebSearch를 생략하고, 사용자가 준 자료로 보고서 구조를 만든 뒤, 서론에 이것이 독립적인 조사가 아니라 사용자 제공 자료를 기반으로 한다는 점을 명시하세요.
- **사용자가 한국어가 아닌 언어로 된 보고서를 원하는 경우**: 구조는 동일하게 유지하되, 본문뿐 아니라 섹션 제목/라벨도 함께 번역하세요 (예: "[개요]" 대신 "Overview"), 본문 텍스트만 번역하지 마세요.
