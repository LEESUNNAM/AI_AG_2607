# 기사 스크랩 보고서 (Article Scrap Report)

웹 기사 하나 또는 여러 개를 스크린샷 기반 아카이브로 만들고, 요청 시 그 위에 문서 보고서와/또는 슬라이드 덱을 추가로 제작합니다. 이 파이프라인은 세 단계로 구성되며 각 단계는 독립적으로도 유용하지만 함께 조합될 때 효과가 커집니다: **스크랩**(Playwright MCP로 이동 및 스크린샷) → **분석**(스크린샷이 아니라 실제 기사 텍스트를 읽음) → **제작**(사용자가 실제로 요청한 docx 보고서 및/또는 pptx 덱만).

## 왜 이런 구조인가

스크린샷만으로는 기사가 존재했다는 사실과 겉모습만 기록할 뿐, 분석 가능한 글이 아닙니다. 보고서/덱을 정확하게 요약하고 올바르게 인용하려면 실제로 추출한 텍스트(제목, 작성자/매체, 본문, 핵심 수치)가 필요합니다. 스크린샷에서 곧바로 "보고서 써줘"로 건너뛰면 내용을 지어내거나 그냥 스크린샷을 묘사하는 수준의 보고서가 나옵니다. 어떤 내용이든 글로 쓰기 전에 반드시 페이지 내용을 먼저 읽으세요.

## 1. 무엇을 스크랩할지 확정

**출처는 네이버 뉴스로 제한됩니다.** 네이버 뉴스(`news.naver.com` / `n.news.naver.com`, 기사에 도달하기 위한 네이버 뉴스 검색/섹션 페이지 포함)에 게재된 기사만 스크랩합니다. 요청이나 대화 맥락에서 대상을 파악합니다:

- 사용자가 네이버 뉴스 URL을 주면 바로 그곳으로 이동합니다.
- 사용자가 URL 없이 주제나 매체명만 말하면, 해당 매체의 자체 사이트가 아니라 네이버 뉴스(`https://news.naver.com`)에서 검색해 네이버 뉴스판 기사를 사용합니다.
- 사용자가 네이버 뉴스가 아닌 사이트의 URL을 주거나 다른 출처를 요청하면, 이 스킬은 네이버 뉴스만 스크랩한다고 안내하고 네이버 뉴스 링크나 검색어를 대신 요청합니다 — 임의로 다른 사이트로 대체하거나 스크랩하지 않습니다.
- 사용자가 이미 세션 중에 네이버 뉴스 기사에 있다면(예: 방금 Playwright MCP로 브라우징한 페이지), 처음부터 다시 이동하지 말고 그 페이지를 그대로 사용합니다.
- 여러 기사를 원한다면(주제, 목록, "이 5개 기사" 등) 각 기사가 네이버 뉴스 페이지인지 확인하며 순서대로 스크랩하고, 분석 단계로 넘어갈 때 누락되지 않도록 목록을 명시적으로 유지합니다.
- 대상이 정말로 모호하다면(URL도 없고, 주제 지정도 없고, 이 세션에서 사전 브라우징도 없다면) 임의로 추측하지 말고 사용자에게 물어봅니다.

또한 요청에서 명확하지 않다면, 어떤 결과물을 원하는지 확인합니다: **스크랩/스크린샷만**, **docx 보고서**, **pptx 발표자료**, 또는 둘 다. 요청하지 않은 결과물을 만들지 마세요 — 불필요한 작업이고 검토 부담만 늘어납니다.

## 2. Playwright MCP로 스크랩

Playwright MCP 도구가 아직 로드되지 않았다면 `ToolSearch`로 `select:mcp__playwright__browser_navigate,mcp__playwright__browser_snapshot,mcp__playwright__browser_take_screenshot,mcp__playwright__browser_click`를 불러오고 필요에 따라 추가합니다. 각 기사마다:

1. `browser_navigate`로 기사에 접속(또는 목록 페이지에서 클릭해서 이동 — 평소 브라우징과 동일).
2. `browser_snapshot`(단순 스크린샷이 아님)으로 실제 접근성 트리 텍스트를 확보 — 제목, 작성자/매체, 게시일, 본문 텍스트를 여기서 읽습니다. 스크린샷은 그림이고, 스냅샷(또는 claude-in-chrome 사용 시 `get_page_text`)이 실제로 분석할 수 있는 것입니다.
3. `browser_take_screenshot`을 `fullPage: true`로 실행해 뷰포트 첫 화면만이 아닌 전체 화면을 기록합니다.

**스크린샷은 `output2/playwright/<주제-슬러그>/`에 저장합니다** — 이 프로젝트의 CLAUDE.md 규칙상 모든 Playwright MCP 결과물은 `output2/playwright` 아래에 있어야 하며, 여러 기사를 스크랩할 때 관련 없는 캡처들과 뒤섞이지 않도록 주제-슬러그 하위 폴더에 정리합니다(예: `output2/playwright/ai-반도체-동향/기사1.png`). 주제-슬러그는 사용자의 주제/요청에서 따오되 파일 시스템에 안전한 형태로 만듭니다.

기사마다 다음을 기록해 둡니다: 제목, 출처/매체, URL, 게시일(표시된 경우), 읽은 본문 텍스트, 스크린샷 경로. 다음 단계에서 전부 필요하므로, 나중에 스냅샷을 다시 읽을 수 있다고 가정하지 마세요(무한 스크롤, 광고 교체, 세션 만료 등으로 페이지가 바뀔 수 있습니다).

## 3. 분석

모든 기사를 스크랩했다면, 글을 쓰기 전에 수집한 내용을 다시 검토합니다:

- 각 기사의 실제 스토리/주장이 무엇인지 — 제목만 보지 않습니다.
- 기사들이 겹치거나 상충하는 지점(한 주제를 다루는 여러 기사가 서로 다른 수치나 관점을 인용하는 경우가 많음 — 이 프로젝트의 리서치 보고서 스킬과 같은 원칙으로, 임의로 하나를 고르지 말고 차이를 명시).
- 실제로 보고할 가치가 있는 내용과 부수적인 내용의 구분(광고, 무관한 사이드바 링크, 스크린샷에 우연히 잡힌 쿠키 배너는 콘텐츠가 아님).

이 분석이 스크린샷 폴더를 보고서로 바꾸는 핵심입니다 — 4/5단계의 목차는 미리 정한 템플릿이 아니라 실제로 찾아낸 내용에서 나와야 합니다.

## 4. docx 보고서 제작(요청 시)

`scripts/create_docx.py`(저장소 루트)에서 `DocBuilder`를 가져옵니다 — 이 프로젝트의 research-report-docx 스킬이 사용하는 것과 동일한 빌더로, 프로젝트 전체 보고서의 시각적 일관성을 유지합니다. 전체 메서드 문서는 해당 스킬을 참고하세요. 스크랩 기반 보고서의 구조는 전체 시장 보고서보다 단순합니다:

```python
import sys
sys.path.insert(0, "scripts")
from create_docx import DocBuilder

doc = DocBuilder(title="<주제> 기사 스크랩 분석", main_color="1F4E79")
doc.add_subtitle("스크랩 일자: 2026년 8월 12일")
doc.add_divider()

doc.add_heading("[개요]", level=1)
doc.add_paragraph("이 문서는 스크랩한 N건의 기사를 분석한 내용입니다...")

doc.add_heading("1. <기사 제목>", level=1)
doc.add_paragraph("출처: <매체명> | 원문: <URL>")
doc.add_paragraph("<핵심 요약 및 분석>")
# 기사별로 반복, 또는 기사들이 하나의 주제로 묶이면 테마별로 그룹화

doc.add_heading("종합", level=1)
doc.add_paragraph("<기사들을 종합했을 때의 시사점>")

doc.add_references([("<기사 제목> (<매체명>)", "<원문 URL>") for each article])
doc.save(f"output2/reports/<주제-슬러그>/<주제>_스크랩_분석.docx")
```

스크린샷 이미지를 docx에 직접 삽입하는 것은 `DocBuilder`의 기본 메서드가 아닙니다 — 사용자가 분석뿐 아니라 실제 스크린샷 이미지도 원한다면, `doc.document`에 접근 가능한 시점 이후 순수 python-docx로 추가합니다(`doc.document.add_picture(path, width=Inches(6))`). 이미지를 본문에 넣을지 경로만 인용할지 불분명하면 확인하세요.

## 5. pptx 발표자료 제작(요청 시)

`scripts/create_pptx.py`(저장소 루트)에서 `PptxBuilder`를 가져옵니다 — 와이드스크린(16:9), 한글 폰트가 깨지지 않는 덱 빌더로, 이 프로젝트의 다른 문서 스크립트들과 색상 테마가 일치합니다.

```python
import sys
sys.path.insert(0, "scripts")
from create_pptx import PptxBuilder

deck = PptxBuilder(main_color="1F4E79")
deck.add_title_slide("<주제> 기사 스크랩 브리핑", subtitle="2026년 8월 12일 기준")

deck.add_section_slide("1. <기사 제목 또는 테마>")
deck.add_content_slide("핵심 요약", ["요약 포인트 1", "요약 포인트 2", "요약 포인트 3"])
deck.add_image_slide("스크린샷", "output2/playwright/<주제-슬러그>/기사1.png", caption="출처: <매체명>, <URL>")
# 기사/테마별로 반복

deck.add_content_slide("종합 시사점", ["...", "..."])
deck.save(f"output2/reports/<주제-슬러그>/<주제>_브리핑.pptx")
```

사용 가능한 `PptxBuilder` 메서드: `add_title_slide`, `add_section_slide`(전면 구분 슬라이드), `add_content_slide(title, bullets, notes=None)`, `add_image_slide(title, image_path, caption=None)`(이미지 자동 스케일 및 중앙 정렬), `add_table_slide(title, headers, rows)`, `add_quote_slide(quote, attribution=None)`(기사에서 인상적인 문장을 그대로 뽑아 강조할 때 유용). 한 슬라이드에 모든 내용을 욱여넣지 말고 기사/테마당 섹션 하나씩 배치하세요 — 발표자료는 정독이 아니라 훑어보는 매체입니다.

## 6. 저장 위치 및 결과 보고

- 스크린샷: `output2/playwright/<주제-슬러그>/`(이 프로젝트의 기존 Playwright MCP 규칙에 따름).
- docx/pptx 결과물: `output2/reports/<주제-슬러그>/` — 원본 캡처 파일과 섞이지 않도록 완성된 결과물을 별도로 보관.

저장 후 채팅에서 사용자에게 알려줍니다: 생성된 파일과 경로, 다룬 기사 수, 내용에 대한 2~3문장 요약 — 보고서/덱 전체 텍스트를 그대로 붙여넣지 않습니다. 일부 기사가 스크랩에 실패했다면(로그인 필요, 삭제됨, JS 오류 등) 결과물에서 조용히 빼지 말고 명시적으로 알립니다.

## 예외 상황

- **유료 구독/로그인 필요 기사**: 이를 명시하고, 보이는 부분(제목/요약 정도)만으로 진행할지 건너뛸지 물어봅니다 — 로그인 장벽을 우회하려 하지 않습니다.
- **사용자가 네이버 뉴스가 아닌 사이트를 스크랩해달라고 요청하는 경우**: 해당 사이트로 이동하지 않습니다. 출처 제한 사항을 설명하고 같은 내용을 다루는 네이버 뉴스 링크나 검색어를 대신 요청합니다.
- **사용자가 스크랩만 원하고 보고서는 원치 않는 경우**: 2단계에서 멈추고, 요청하지 않은 문서를 만들지 않습니다.
- **기사 1건 vs 여러 건**: 파이프라인 자체는 동일하지만, 기사 1건에 `add_section_slide`/다수 docx 섹션을 쓰는 건 보통 과합니다 — 콘텐츠 슬라이드 1개, docx 섹션 1개면 충분하며 규모에 맞게 판단합니다.
- **스크린샷을 docx에 직접 삽입하길 원하는 경우**: 경로만 인용하는 것이 아니라 — 4단계 마지막의 안내를 참고합니다.
- **기사들이 서로 상충하거나 하나는 명백히 오피니언/사설, 다른 하나는 뉴스인 경우**: 모두 하나의 평면적 요약으로 뭉뚱그리지 말고 분석에서 이 구분을 명시합니다.
